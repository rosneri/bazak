# Goldfish delivery review

## What this proposes

A local shopper can search for products, see the reply arrive in pieces, refine results, and reopen the conversation. The model identifies the request. An optional planner can use relevant earlier chats to fill gaps in a broad request. Application code validates the proposed search, applies catalog constraints, and saves the answer before announcing completion. A second app displays persisted scores and evidence from labeled evaluation runs.

## How the existing system works, per this document

The shopper app is a Next.js starter, and the management app has configuration. The repository has initial Zod contracts for chat and discovery, a DummyJSON page adapter with tests, and a partial Prisma evaluation store backed by local PostgreSQL. The route handlers, durable turns, evaluation runner, and user interfaces are planned work. [Concepts brief](concepts_brief.md#analysis) · [Project status](../PROJECT_STATUS.md)

## Findings

1. **Blocker · Build profile selection.** “Build target or alias” leaves the most important wiring choice open. Name the module specifier the web routes use, the Next configuration that resolves it, the commands that select and start each build, and how those outputs stay distinct. A Node evaluation runner cannot inherit a Next-only alias. Give its production and fixture entry points explicit static imports of the same composition factories. Keep API contract tests on a handler factory with injected services. Verify that a default build with a key absent serves saved data and that the fixture build exercises the real route with zero external calls. [Evaluations and build profiles](delivery-plan.md#evaluations-and-build-profiles)
2. **Blocker · Outcomes for planned groups.** The planner can ask a clarifying question for one group. The discovery contract has three outcomes and none carries that question. Define what the service persists and streams when one group asks for clarification and another returns products. Specify whether a valid planner question suppresses its lookup, and distinguish it from fallback after invalid output or timeout. Include one mixed example showing the question, successful cards, and exactly one group's catalog activity. [Catalog and discovery](delivery-plan.md#catalog-and-discovery) · [Conversation service](delivery-plan.md#conversation-service-and-persistence)
3. **Major · Cheaper follow-up and current facts.** The primary journey asks for a cheaper option after showing two differently priced cards. Specify the comparison baseline for a generic follow-up in one group, when there are several plausible groups, and which prior constraints carry forward. Seed at least one fixture below the chosen threshold. Define a validated detail intent and its persisted result for live price or stock checks. Resolve the product ID from a prior visible snapshot and allow the detail result to report out-of-stock status. [Catalog and discovery](delivery-plan.md#catalog-and-discovery)
4. **Major · Retry after a lost response.** An empty retry request can be resent after the first retry has already failed and silently start a third attempt. Include the expected failed attempt number in the request and compare it inside the acquisition transaction. For an already-claimed generation, return the current state or replay the completed reply. Define recovery for a lost create response too, including whether an empty extra thread is tolerated or a client-generated create ID makes creation idempotent. Specify exact JSON error codes and status/replay event sequences for contract tests. [Shopper HTTP and browser](delivery-plan.md#shopper-http-and-browser)
5. **Major · Evaluation boundaries and management freshness.** Identify how evaluation conversations are scoped so fixtures can seed prior chats without entering shopper history or a different case's planner context. State which runs management reads and how the browser test points management and the evaluation runner at the same isolated database. Use a request-time read so the dashboard sees runs recorded after startup and production builds can run without a database connection. Keep model and catalog composition in the shopper app and evaluation runner. [Evaluations and build profiles](delivery-plan.md#evaluations-and-build-profiles)
6. **Major · Test commands and timing proof.** Name commands for package unit/API tests, PostgreSQL integration, and Playwright. The existing adapter uses `node:test`; the root check discovers package `test` scripts through Moon. Keep those scripts service-free and give the happy-path database and browser checks isolated connection setup and explicit commands. In Playwright, hold the terminal chunk behind a controllable fixture gate, assert text is visible while the gate is held, then release it and verify the saved cards after refresh. State whether first output is measured at server emission or browser observation. A happy database integration and fake-based edge tests leave real SQL locking unverified. Include that in the manual two-tab check.
