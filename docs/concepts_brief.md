# Shopping copilot concepts brief

**Neriya Rosner · 2026-11-23 · Reviewed concepts brief**

## Overview

A local shopper can ask for products in ordinary language, inspect catalog cards, narrow the results and return to that conversation. A reviewer can start both local apps, run independently labeled examples and inspect what the copilot actually returned. The assignment asks for a coherent discovery experience and for concrete reasons that the author can defend for each major choice. The primary acceptance journey is “two fragrances under $50,” followed by a cheaper suggestion, a reload and a return through chat history.

## Analysis at design time

This brief preserves the design assumptions before implementation. See the [current architecture](architecture.md) and [handoff](../PROJECT_STATUS.md) for the implemented behavior.

The repository already contains schemas for a chat message, a send request, search criteria and a catalog snapshot. The DummyJSON adapter validates keyword and category pages. The web app currently displays a starter page. The management app has configuration, and the partial Prisma setup defines an evaluation record. The remaining work includes model calls, retrieval policy, durable conversations, streamed rendering, labeled evaluation execution and both user interfaces. The [architecture sketch](architecture.md) describes the intended behavior and the [earlier comprehension review](comprehension_report.md) records decisions on mixed search results, concurrency, deletion and replay.

The central tension is between quickly showing an answer and being able to stand behind it. The model can interpret “under $50” and resolve a reference to an earlier product. Only the application can inspect catalog pages, compare prices, filter stock and decide whether every candidate was examined. A search that hits its page limit can return matching cards with a partial-coverage explanation. A shopper asking for the cheapest option should know whether the service compared the whole group. Historical cards retain their original values, and questions about current price or availability require a fresh lookup.

A browser can display text and product previews before a database commit. A disconnect at that moment leaves the shopper uncertain whether the reply was saved. A stable turn ID, one active attempt per conversation and a final event sent after a transactional commit let the browser read the actual outcome and recover safely. A second tab keeps its draft when the thread is busy. Clearing browser storage leaves saved threads on the server. If an explicit thread-clear action is later exposed, it removes the thread from history and invalidates its active attempt atomically. A late model response cannot recreate it, and the old URL links back to history. A failed lookup for chairs alongside matching lamps is an outcome worth saving. “Try the chairs again” is a new turn limited to that group. A retry after a lost model stream belongs to the original user message.

A deterministic model and catalog let a test hold back the final text chunk and prove that the first chunk reached the screen. They also make strict budgets, stock, clarification, off-catalog abstention and mixed results repeatable. Their scores measure contract and application behavior. The live SDK and catalog need a separately labeled smoke or evaluation if available. A small fixture suite cannot measure how often a live model interprets unfamiliar wording correctly.

## Goals and scope

- Support local thread creation, history, continuation, clarification, off-catalog requests, multi-intent search, recovery and replay. Ground cards and factual claims in validated catalog observations.
- Run a Next.js shopper app and a separate local management app for persisted labeled evaluation runs. Keep ordinary attempt observations available without assigning accuracy to unlabeled conversations.
- Cover features with readable unit tests for normal behavior and realistic edge cases. Use API tests to verify request, response, status and stream contracts. Reserve integration and browser tests for happy flows. Exercise user-visible failure and recovery manually as well.
- Complete the locally runnable source and README. Delivery scope excludes deployment, external submission, payments, shared accounts, remote administration and a general-purpose widget catalog.

## Key decisions and staging

1. Establish feature-owned Zod schemas with final `.describe(...)` metadata for every schema and field. Preserve the existing models and derive boundary types from them.
2. Connect catalog, model and storage behind narrow contracts. Bound time and page usage, persist outcomes for each attempt and represent incomplete coverage explicitly.
3. Demonstrate a single real input-to-card-to-replay path using POST with SSE, then add continuation, concurrency and recovery. Limit the first UI to one registered product presentation.
4. Run the labeled suite through the same conversation service. Display case evidence, applicable scoring denominators, time to first visible output and total duration. Report fixture and live observations distinctly.
5. Verify setup and the happy shopper journey from an isolated local database. Document failure behavior, known limits and concrete framework alternatives in the README.

**Author decision on broad requests.** The existing structured intent call also decides whether each actionable search is ready or needs query planning. “Two fragrances under $50” is ready. “Something cheap and cool” lacks a product target and goes directly to clarification. For “show me a few fragrances,” call a separate, low-cost query-planning agent for this request. Provide a bounded selection of relevant earlier chats from this local shopper. The agent proposes search criteria for this turn. Validate them, retain the category and all explicit current constraints, and use the normal discovery service to run the query. Empty relevant history skips the extra model call and uses the category alone. A generated question for one group leaves independently actionable groups available. Inferred preferences can guide that turn’s first query or ordering. They cannot silently impose an old budget. Clear requests, current-thread references that are already resolved, and off-catalog turns bypass this agent. Its inferred choice expires with the turn. A single global cheapest or popularity rule would lose this context.

Use the assignment-allowed OpenAI model with a short structured response and low reasoning effort where supported. Record when the extra call was used. A labeled case should seed an earlier conversation and check the actual query, alongside cases that demonstrate the history and model-call bounds.

**Independent review resolutions.** The shopper’s current constraints take precedence. A cheap first-query hint can reserve remaining page capacity for the original category if it underfills. In a single group, “cheaper” means strictly below the lowest displayed price. A request about today’s stock can refresh only a previously shown product. Capped or changing pagination qualifies claims about the observed candidates. The shopper sees verified cards promptly. Time to first content excludes status messages. A failed provider stream leaves previews visibly unsaved and can be retried using the observed attempt number.

The [delivery plan](delivery-plan.md) records engineering defaults for budgets, profiles, contracts and retry behavior separately from the author’s choices. The implementation will test semantic product relevance on seeded cases, verify concurrency in two tabs, and show the difference between fixture behavior and any observed live-provider run.
