# Bazak local delivery plan

**2026-11-23 · Formal implementation plan · Neriya Rosner**

A shopper should be able to ask for two fragrances under $50, see text arrive and catalog cards appear, reload, then ask for a cheaper option in that same conversation. A reviewer should be able to run a labeled suite locally and see which checks passed and how long each turn took. The unit of delivery is that working journey across two local Next.js apps and PostgreSQL. The [assignment](../assignment/instructions.md), [architecture](architecture.md), [earlier review](comprehension_report.md), [working agreements](../AGENTS.md) and [delivery handoff](../PROJECT_STATUS.md) establish the baseline.

**Historical design.** The checklist below preserves the proposed acceptance criteria. Current delivery evidence is in the [handoff](../PROJECT_STATUS.md) and differences are in the [drift report](2026-11-23_DRIFT_REPORT.md).

The [concepts brief](concepts_brief.md) records the author’s choices. The [independent delivery review](delivery-review.md) informed the contracts below. Local numeric budgets, the relative-price baseline, and the retry payload are engineering decisions. They can be tested and explained independently of the author’s selection of the SDK, build profiles, history-aware planner and test strategy.

## Contracts between owners

### Catalog and discovery

Keep the existing `ProductSnapshot`, `DiscoveryCriteria`, `IntentDecision`, `CatalogQuery` and `ProductCatalog.findPage(query, signal?)` exports. Add category validation from the known DummyJSON slugs and a single-ID detail lookup for a follow-up asking for the current price or stock of a particular result. Refresh immediately for a current-facts question. A replay always uses the recorded snapshot. Use the prior criteria, text and visible snapshots to resolve references. For “a cheaper one” after one visible result group, preserve the group’s explicit filters, require a price strictly below the cheapest displayed card, and return the cheapest observed qualifying match. A named card sets its own comparison price. If several groups could be meant, ask which one. Seed the demo with a qualifying cheaper item. A validated detail decision may reference only an ID previously shown in this thread. Revalidate that ID before fetching current data. Persist its new observed snapshot, including zero stock, alongside the question. The earlier card keeps its original value.

`createDiscoveryService(catalog)` accepts validated criteria and an abort signal and returns a labeled group per request, in request order. Represent a lookup group with its criteria, label, observed products and a discriminant for matched, empty or lookup-error. The conversation layer also accepts group-level clarify (carrying a question) and off-catalog (carrying scope guidance). These groups consume zero catalog calls and do not block specific sibling searches. For “two lamps, and a gift for someone,” the lamp group can return cards and the gift group can ask who it is for. Save both parts in order. Record exhaustive or partial coverage on successful lookups. A reported lookup error can complete a turn. The group's label and stable position let a later turn retry just that request.

Start with at most three search groups per turn, three pages of 20 per group, a default of three visible results and at most ten per group. Include these limits in the intent schema or enforce them before querying. If the input exceeds supported limits, explain or clarify the limit. Prefer a known category to a keyword query. If both fields are present, narrow the category candidates by the supplied terms. Validate the slug, use only the fixed catalog host and allowlisted paths and encode every parameter. Apply stock > 0 and the requested price comparison, including the difference between “under” and “up to.” Normalize exclusive dollar limits to the preceding cent and compare in integer cents. Keep the first snapshot per ID, rank by requested price direction with stable ties, otherwise preserve returned catalog order, then truncate. For an underspecified category, use the history-aware query and fallback rules below. When the cap interrupts scanning, report what the inspected pages yielded. A zero-match partial result must disclose that there may be more results. Track actual requests including failures. A stable observed scan has consistent totals, offsets, and distinct IDs across pages. Downgrade coverage to partial on observed drift or duplicate IDs. Even an exhaustive scan describes those observed pages at retrieval time because the upstream catalog offers no snapshot isolation. Use representative searches to record whether these defaults are adequate.

### Conversation service and persistence

The composition root constructs `createConversationService({ repository, model, queryPlanner, discovery, clock })` and conversation-management operations for create/list/load. The conversation feature owns SDK-based intent generation and reply streaming with an injected language model. Validate the complete decision before any lookup. Use the thread's recent ordered messages, earlier criteria and referenced cards as context, use at most eight recent turns with 500 characters of text per message and compact visible-card references. The application builds every product part from returned snapshots. Deliver each verified product group as soon as it is ready. Generate all product facts, counts, coverage statements and comparisons from validated results. For a discovery reply, stream only approved framing. Constrain generated phrases to a small list of safe transitions, buffer until a phrase matches, and emit the matched phrase. Skip unmatched phrases. Render explanatory facts through templates. An interrupted provider stream ends this attempt as recoverable; preserve any visible cards as unsaved previews until replay. Never emit a done event on failure. Clarify and off-catalog turns make zero product calls. A malformed decision, provider timeout or truncated model stream produces a recoverable attempt failure. The default production provider is OpenAI, the model is `gpt-6-luna`, and fallback is unset.

**Decision gate and history-aware query planner.** Reuse the structured intent model call. A validated discover decision returns ordered groups. Each actionable search is shaped as `{criteria, readiness: "ready" | "needs-planning"}`. “Two fragrances under $50” is ready and goes straight to discovery. “A few fragrances” has a target but needs a query plan for this turn. “Something cheap and cool” has no clear target and yields the existing top-level clarify decision. The schema describes the readiness field and both outcomes. For mixed requests, route each group independently in original order. Only needs-planning groups read relevant history. Invoke the planner only when that read yields relevant evidence. The bounded planner runs at most once per turn attempt. This reuses the existing SDK decision call and requires no separate routing call or vendor-specific Decisions API. Read at most five earlier completed turns from other chats for the local shopper that contain a validated search for the same category, newest first. Provide matching structured criteria and relevant shopper excerpts only (up to 240 characters each). Treat prior messages as shopping evidence. Current-thread follow-ups with resolved references, explicit fully specified searches, direct product details, clarification and off-catalog requests skip this step. For several eligible groups, use one batched call and correlate results by group index. Repository selection excludes the active conversation and evaluation fixtures from unrelated runs.

The planner receives category, current explicit constraints and bounded history. It returns a per-group query proposal with soft preferences or a clarifying question. Preserve current explicit constraints and resolved same-thread references. Treat older budgets or price orders as soft ranking hints. An inferred keyword can narrow a first query inside the requested category. Reserve at least one page for the original category if the hinted query underfills, deduplicate by ID, and remain within the same page and deadline budgets. Use only verified category matches, including when mapping a hinted category query to the upstream API. Inferred hints cannot change the explicit price limit, suppress base-category results on underfill, or justify claiming broader coverage. A targeted query that fills the display can end with partial category coverage. Show a concise applied preference such as “lighter scents first” using supported product attributes, leaving quotations and previous chat text private. A valid planner question suppresses only its own lookup. Empty history bypasses the model and uses the category alone. Invalid or unavailable planner output also falls back to the base query. Save the per-turn criteria, planner disposition (skipped, used, clarification or fallback) and call counts. No global shopper preferences are written.

**Per-attempt budget.** One structured intent call (up to 768 output tokens), at most one batched planner call (256) and one streamed reply call (512). Use the assignment model for all three, with low reasoning effort for planning when supported, and disable automatic SDK retries. Give intent 20 seconds, planner 8, retrieval 25 and reply 25, all within the shared 90-second lease. Share up to nine page requests across the three groups, including failed attempts. Category validation uses a known allowlist and requires no repeated metadata lookup. A detail turn needs at most one product GET. Log call counts and elapsed times. Record time to first server-emitted shopper content (text or card); status is excluded. A browser test separately verifies when actual text becomes visible.

The repository supports create, list, load, read relevant earlier turns, begin turn, begin retry, finish, and mark failure/interruption. A thread has a UUID, title and last-activity timestamp. Sort threads descending by last activity then ID, and sort turns by a monotonic ordinal unique within the thread. A turn stores the stable user text, state, current attempt number, validated decision and at most one final assistant message with ordered, versioned parts. Each attempt stores start, cutoff, end, outcome, catalog calls, time to first visible output and total duration. Represent times in UTC, durations in nonnegative milliseconds and absent first output as null. Present failed attempts in history with actionable status. Preserve attempt outcomes when retrying.

Serialize per-thread acquisition with a short PostgreSQL transaction and a row lock or equivalent conditional write with a uniqueness invariant. Check duplicate turn ID and original text first. A competing new ID is busy while an unexpired attempt runs. New turns on different threads are independent. Use a 90-second lease, abort provider work by that deadline, and treat an expired attempt as interrupted on the next read or acquisition. A retry carries the failed attempt number the shopper saw. In the same transaction, compare the expected and current numbers and require failed/interrupted state before incrementing the attempt number and reusing the same user message. Completion requires a matching active, unexpired attempt and atomically saves answer, outcome and thread activity. Late writes and duplicate retries cannot overwrite the winner. Never hold a SQL transaction across a catalog or model call. Titles start as “New chat” and use the first user text once submitted. Corrupt saved payloads produce a recoverable thread-specific error. If storage is full or unavailable, label streamed content unsaved and reconcile by reading authoritative state when possible.

### Shopper HTTP and browser

| Operation                                           | Wire contract                                                                                                                                                                                                                               |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/conversations`                            | 200 JSON `{conversations: [{id,title,createdAt,updatedAt}]}` in history order.                                                                                                                                                              |
| `POST /api/conversations`                           | JSON `{id}` with a client-generated UUID. First create returns 201 JSON `{conversation: {id,title,createdAt,updatedAt}}`; repeating that ID returns 200 with the same thread.                                                               |
| `GET /api/conversations/[id]`                       | 200 JSON `{conversation,turns}`. Each ordered turn carries `turnId,text,state,attempt,assistant`; assistant is null until committed, then contains ordered parts. States are `running`, `completed`, `failed`, `interrupted`.               |
| `POST /api/conversations/[id]/turns`                | JSON `{turnId,text}` using the existing client-generated UUID. An accepted send returns 200 SSE. A repeated ID with the same text returns stored status, and replays the saved reply if complete. Changed text under the same ID conflicts. |
| `POST /api/conversations/[id]/turns/[turnId]/retry` | JSON `{expectedAttempt}`, a positive integer. Matching terminal failed/interrupted state starts one attempt. Repeated or stale generation returns present status and replays a completed reply. A future generation conflicts.              |

Before streaming, return JSON `{error:{code,message}}` with 400 for invalid input, 404 for missing thread or turn, 409 for a busy thread or changed duplicate text and 503 for unavailable storage. Use codes invalid_input (400), not_found (404), thread_busy, turn_conflict or attempt_conflict (409), corrupt_thread (500), and storage_unavailable (503). Include no internal exception text. For SSE use UTF-8 `text/event-stream`, disable caching and send one JSON `data` frame per event with a `type` discriminator and `turnId`. Events are `status` (state and attempt), `text-delta` (text), `products` (one versioned group part), `done` (canonical committed assistant message) and `error` (code, message). Flush incremental events. Only emit done after commit. End failed streams with an error. A completed replay emits status then done with the saved reply. Other duplicate states emit status then close. A client tracks the active ID, discards stale previews, handles UTF-8 and frame boundaries across chunks, and reads the saved turn after a disconnect. Poll pending state with a bounded delay until terminal or lease expiry. Offer retry on the same ID only for a failed or interrupted turn. Keep a busy draft. Handle a lost create/send response without duplicating user messages on a turn resend.

Use one registered versioned product surface backed by the shared shadcn primitives. Document the implemented local message-part format accurately; general A2UI protocol support and multiple card strategies are future work. Both the live `products` event and replay feed the same renderer. The card shows title, description, price, thumbnail or image fallback. Never render executable or unregistered components from model data. Preserve URL-addressable threads across reloads. Clearing shopper browser storage preserves server history. Explicit thread deletion is outside the initial UI. If that action is introduced, atomically remove the thread from history and invalidate its active attempt. Its old URL must offer a return to history and a late completion must never recreate the cleared thread.

### Evaluations and build profiles

Run independently labeled prompts through the same conversation service and observe actual decisions, returned products, calls and timings. Score intent equality, product constraints and abstention separately. Include independently chosen acceptable fixture IDs or relevance labels, requested count and sort checks per group. Record provider/transport failures separately from semantic disagreements. A missed expected product group or an empty response to a case requiring a match fails constraint satisfaction. Correct abstention requires the expected clarification/off-catalog decision and zero lookups. Case-independent live chat observations receive no labels or accuracy grades. Store run identity, profile, case name, timestamps, expected versus actual evidence and nullable check results. Show each metric's scored denominator. Report first visible output separately from duration. Re-importing an identical batch by ID is idempotent; validate the entire input before writing and reject conflicting data under an existing ID.

Web routes import `@bazak/services`. Configure its static alias in Next’s Turbopack resolver, with a TypeScript path for editor/typechecking, to `src/server/services.production.ts` by default or `src/server/services.test.ts` for a fixture build. Bind both apps’ local dev/start commands to 127.0.0.1. The `build:fixture` and `start:fixture` scripts select the same fixture config and use a separate `.next-fixture` directory. Standard builds use `.next`. The chosen profile is fixed when building. Production injects Prisma, real DummyJSON and the SDK model. The fixture profile injects a scripted model and planner, seeded catalog and controllable clock. No credentials are needed to start either app or read history. Key validation occurs on the first real inference. An actionable configuration error leaves history readable.

All shopper database routes and the management dashboard read at request time. Both builds must succeed with the database offline. Management reads only persisted evaluation results, including runs created after the app starts. The evaluation CLI uses explicit production and fixture entry modules with static imports of the same composition factories; a Node CLI does not inherit Next’s alias. Its default command uses fixtures. Keep shopper data in a shopper scope. Assign a unique scope per evaluation run and case so a case can seed its own previous chats; apply the scope to create, list, read and planner history selection. Keep fixture and production scores labeled. Browser verification points both apps and the runner at the same isolated migrated local test database.

## Verification and trade-offs

- [ ] First prove one vertical slice with a scripted streamed reply, one catalog card and replay. Early in delivery, when credentials and network are available, smoke-test real structured intent, the low-cost planner and streaming with the allowed provider. Record any unsupported provider option and exercise the documented fixture demo separately.
- [ ] Use the existing adapter’s `node:test` and `tsx` runner pattern for service-free feature and HTTP contract scripts. Run `pnpm test` (Moon package tests), `pnpm test:integration` (happy-path Prisma), and `pnpm test:e2e` (happy-path Playwright). Only the latter two require the isolated migrated PostgreSQL database. Hold the fixture’s final chunk behind a test-controlled gate until Playwright observes visible text, then release it and reload. Test exact retry generation, including a delayed duplicate after the retried attempt has failed. Manually send competing turns in two tabs using real PostgreSQL and verify one active attempt and preserved draft.

- [ ] Run the documented pinned toolchain setup, `pnpm install`, `pnpm db:generate`, `pnpm db:up` and both app commands on ports 3000 and 3002. Verify a database restart preserves two threads and a recorded evaluation using the named volume.
- [ ] Run feature unit suites, request/response contract tests, the happy-path database integration, Playwright and `pnpm check`. Use controllable streamed chunks to prove incremental rendering before the terminal event. Exercise failure, retry and recovery through focused unit/API contracts and a manual shopper check. Keep integration and browser suites on happy flows.
- [ ] Run cases for clear search, strict budget, contextual follow-up, a broad category with relevant history from a different test chat, the same category with empty history, vague input, off-catalog input and independent multi-intent constraints. Isolate fixtures per case to avoid accidental history leakage and inspect the emitted query plus planner call count. Record deterministic results with the fixture profile. If authorized credentials and connectivity are available, run a small production-profile smoke with OpenAI and DummyJSON, record its observed outcome separately and avoid exposing keys. If unavailable, state exactly which external path remains unverified.
- [ ] In the README, compare the SDK to direct OpenAI calls (structured-output parsing and streaming ownership) and a multi-agent framework such as Mastra (a second orchestration layer around a bounded search).
